# R1.4 / C2 — CPU speed definition via IPC: validation + paper fix

Covers checklist item **C2** (Meret: "CloudSim, NetworkCloudSim, DISSECT-CF and
SimGrid define host CPU speed via IPC variants — context-dependent (OS, apps), must
be measured per configuration; more accurate in principle but harder to obtain")
and a related inaccuracy in `paper/sections/experimentExecution.tex:66`.
Paths are relative to the repo root.

---

## 1. Paper fix (not applied — for Max to write)

**Where:** `paper/sections/experimentExecution.tex:66`, sentence:

> The mean of these 30 IPC values was then taken to be used to configure the cloud simulators.

**Problem:** only CloudSim and NetworkCloudSim use the measured IPC. DISSECT-CF
reads it but never uses it; SimGrid uses a fixed FLOPS value that is not derived
from IPC (evidence in §3).

**Suggested replacement (wrap in `\rone{}`):**

> The mean of these 30 IPC values was then used to derive the MIPS rating of the
> host in \textit{CloudSim} and \textit{NetworkCloudSim}. For \textit{DISSECT-CF},
> the processing capability was set to one instruction per tick, so that the
> instructions of a job correspond to its CPU-seconds, and for \textit{SimGrid} a
> fixed host speed in FLOPS was used. As all workloads are defined relative to the
> host's capacity (CPU utilization over time), the absolute CPU speed cancels out
> and does not affect the simulated energy consumption.

Notes on the wording:
- Says "MIPS rating", not "per-core MIPS": the code divides by the core count, so
  the value is not the true per-core MIPS (see §4).
- Optional extra (transparency, see §5): report the spread, e.g. "(Sock Shop:
  0.71 ± 0.01; Train Ticket: 0.88 ± 0.14)".

**Related sentence, same paragraph (optional):** "the Instruction Per Cycle (IPC) or
variations of it are needed for all simulators except \textit{OpenDC}" — SimGrid's
FLOPS is not an IPC variant (§2), so "except OpenDC and SimGrid" or "instruction-
or FLOP-based CPU speed" would be more precise.

- Agree: MIPS and instructions/tick are IPC-derived throughput rates; IPC is

- Disagree: SimGrid's FLOPS is not an IPC variant. "More accurate in principle"
  was not tested by this study, because CPU speed cancels out (§4).

## 4. Why CPU speed has no effect on results (workloads are relative)

Workload traces are measured CPU usage per service (cores used per 5 s interval,
`traces/<system>/<scenario>/<users>/<rep>/services/*_cpu_usage.data`). Each
simulator converts this back into "work" using the host's own speed, so the speed
cancels; the power models only see utilization u (P = P_idle + (P_max − P_idle)·f(u)).

| Simulator | Work handed to the simulator | Resulting time | Evidence |
|---|---|---|---|
| CloudSim / NetworkCloudSim | cloudlet length = 300 s × MIPS; utilization = usage / cores | 300 s regardless of MIPS | `TraceExperiment.java:259–260`; `simulators/cloudsim/modules/cloudsim/src/main/java/org/cloudbus/cloudsim/UtilizationModelMicroservices.java:46` |
| DISSECT-CF | exectime_s × cores instructions, at 1 instr/tick/core | = original seconds | `.../examples/custom/SingleJobRunner.java:119–120` |
| SimGrid | flops = 5 s × fraction × host_speed | = 5 s × fraction | `simulators/simgrid/simgrid-template-s4u-master/simple.cpp:75` |

Consequences:
- The IPC calibration only matters for **absolute** workloads (instructions/FLOPs)
  or when replaying a workload on a different simulated machine. This study did
  neither, so it provides no evidence for or against "more accurate in principle".
- Two unit errors therefore have **no effect** on results:
  - CloudSim MIPS is 16× too small: perf's "insn per cycle" is already per core, so
    dividing by `pesNumber` (`TraceExperiment.java:126`) gives ≈ 93 MIPS instead of
    ≈ 1,494 (2.1 GHz × 0.711).
  - SimGrid speed is 10⁶× too small: `core_gflops * 1000` → 281,600 flop/s instead
    of 281.6 GFLOPS (`traces/platform.xml:6`).

## 5. The IPC measurement itself

- Script: `trace-generation/get_ipc.sh:6`
  `perf stat -a -e instructions,cycles sleep 60` × 30 → system-wide (all processes,
  incl. monitoring + kernel); `cycles` counts unhalted cycles only.
- Aggregation: `trace-generation/gen_traces.py:89–95` → mean into
  `traces/properties.json`.
- One value per application; not per scenario or user load. The script does not
  start the load, so the measurement conditions are not recorded.

| Data | n | mean | sd | range |
|---|---|---|---|---|
| `trace-generation/ipc_sockshop.data` | 30 | 0.711 | 0.012 | 0.70–0.76 |
| `trace-generation/ipc_trainticket.data` | 30 | 0.879 | 0.139 | 0.76–1.06 |

**Train Ticket is bimodal:** runs 1–12 ≈ 1.05, runs 13–30 ≈ 0.77. The mean (0.879)
matches neither mode. This directly supports Meret's "context-dependent, must be
measured per configuration", and is worth a sentence in the paper or response letter.
